<Your Task>
Write a CLUSTER behavior summary for the WHOLE cluster (not one medoid journey)
AND describe how its trajectory differs from its parameter-space-matched neighbors.

Primary inputs (required upstream):
1. This cluster's `output/medoid_trial.yaml` — archetype behavior.
2. Parameter-space pair contrast files that touch this cluster (`parameter_space_pairs/c*-c*/output/contrast.yaml`)
   — boundary evidence under matched initial conditions.
3. Optional `processed/context_cluster.md` — cluster size, collision rate, parameter ranges
   (not a single-trial timeline).

This prompt runs **per cluster, independently** — you do not see any other
cluster's label, caption, or evidence, and the pipeline does not read one
cluster's summary before writing another's. A separate review pass (after all
clusters are summarized) compares labels across the run and fixes duplicates;
do not try to guess or avoid other clusters' names here.

**You invent `label`.** Short **outcome archetype** (2–4 words), the kind of
name that fits a legend (`Smooth Pass`, `Yield`, `Cut-in Collision`, `Brake Rear-end`). One
mechanism. The why belongs in `caption`. Closed style set lives in
common_sense (`§Cluster label`) — prefer one of those before inventing a new
archetype.

**Cluster provenance:** MFPCA followed by HDBSCAN was run on the **whole
trajectory**. A cluster therefore groups trajectory shape and termination, not
necessarily one interaction intent. At a collision/behavior boundary, one
parameter-space edge may be a pass attempt that collides while another is a
yield attempt that also collides, even when their trajectories look similar.
Do not force those boundary cases into the medoid's resolution; use the
pattern of pair readings to describe the mix.

The clustering already groups whole trajectories. Describe what this cluster
shares with a neighbor and what still differs. Do not recommend a merge, a
split, or a different number of clusters.
</Your Task>

<Mandatory Workflow & Chain Of Thought>
1. Medoid first: restate this cluster's named-vehicle `resolution`, outcome, and
   1–2 sentences of `motive_summary` from `medoid_trial.yaml`. Draft a **2–4 word**
   `label` as an outcome archetype (Pass / Yield / Collision / Stop / Rear-end
   family). `label` is the only place that may say `Late Yield`. Put the why
   in `caption`.
2. Neighbor-by-neighbor: for EACH Parameter-space pair block touching this cluster:
   - Prefer the contrast YAML (`behavior_similarity`, critical_divergence, evidence).
   - Copy pair `behavior_similarity` onto this neighbor. It is the behavior of
     the two boundary trials, not the whole-cluster trajectories. Do **not**
     require this cluster's boundary side to match the medoid YAML. The medoid
     is one interior point; a collision-boundary cluster can have a stay-behind
     edge and a go-through edge. That mix is rolled up in step 4 — never override
     a pair call to `inconclusive` just because the edge ≠ the medoid.
     | pair `behavior_similarity` | this neighbor `behavior_similarity` |
     | ---- | ---- |
     | missing contrast file | `ambiguous` |
     | `distinct` | `distinct` |
     | `similar` | `similar` |
     | `inconclusive` | `inconclusive` |
   - `distinct` = the two boundary trials differ in resolution family, outcome, or a
     persistent stay-ahead versus overlap.
   - `similar` = the two boundary trials share a resolution family and the same outcome.
     Name the trajectory detail that still differs.
   - `inconclusive` = this pair does not name the difference.
     Not a missing file (`ambiguous`) and not a `neighbor_behavior` value.
   - `ambiguous` = missing card.
3. Read the pattern of neighbor `behavior_similarity` values (not “does one edge match the medoid”).
   A collision-boundary cluster often shows mixed calls: some `distinct`
   (stay-behind vs overlap / go-through) and some `similar` (same family and
   same outcome). That pattern is the intended product.
   Whole-trajectory MFPCA+HDBSCAN can group those trials together: do not relabel
   the boundary cases merely to make them agree with the medoid.
4. Roll up `neighbor_behavior` from those values. This is not a clustering change:
   - `distinct` — neighbors are mostly `distinct`, and those edges tell the SAME
     geometry family as each other (all stay-behind, or all go-through).
   - `similar` — neighbors are mostly `similar`.
   - `mixed` — this cluster’s boundary sides mix families, OR the neighbor list
     has at least one `distinct` AND at least one `similar`. Describe the mix.
     Do NOT use this merely because one boundary trial ≠ the medoid string.
   - `ambiguous` — missing medoid_trial.yaml / contrast.yaml.
5. `distinct_from_neighbors` is computed by the pipeline from neighbor_comparison
   (true only if every `behavior_similarity` is `distinct`) — do not invent it.
6. **Label is yours.** Invent a 2–4 word outcome archetype `label`. One
   mechanism. Richer nuance belongs in `caption`.
</Mandatory Workflow & Chain Of Thought>
