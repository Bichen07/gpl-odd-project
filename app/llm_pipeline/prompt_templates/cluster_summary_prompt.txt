<Your Task>
Write a CLUSTER behavior summary for the WHOLE cluster (not one medoid journey)
AND judge whether it separates well from its parameter-space-matched neighbors.

Primary inputs (required upstream):
1. This cluster's `output/medoid_trial.yaml` — archetype behavior.
2. Parameter-space pair contrast files that touch this cluster (`parameter_space_pairs/c*-c*/output/contrast.yaml`)
   — boundary evidence under matched initial conditions.
3. Optional `processed/context_cluster.md` — cluster size, collision rate, parameter ranges
   (not a single-trial timeline).

**Cluster provenance:** MFPCA followed by HDBSCAN was run on the **whole
trajectory**. A cluster therefore groups trajectory shape and termination, not
necessarily one interaction intent. At a collision/behavior boundary, one
parameter-space edge may be a pass attempt that collides while another is a
yield attempt that also collides, even when their trajectories look similar.
Do not force those boundary cases into the medoid's single motive; use the
pattern of pair verdicts to expose this mixture.

Decide whether neighbors look mergeable, whether the medoid is unlike boundary
cases (finer split?), or whether the cluster is well separated.
</Your Task>

<Mandatory Workflow & Chain Of Thought>
1. Medoid first: restate this cluster's primary_motive, outcome, and 1–2 timeline
   concludes from `medoid_trial.yaml`.
2. Neighbor-by-neighbor: for EACH Parameter-space pair block touching this cluster:
   - Prefer the contrast YAML (separation_call, critical_divergence, motives).
   - MAP pair `separation_call` into this `verdict` faithfully. These are
     different YAML fields. `justified` / `over_fine` exist ONLY on the pair
     card — never write them here. Do **not** require this cluster's boundary
     side to match the medoid YAML. The medoid is one interior point; a
     collision-boundary cluster can have a stay-behind edge and a go-through
     edge. That mix is rolled up in step 4 — never override a pair call to
     `inconclusive` just because the edge ≠ the medoid.
     | pair `separation_call` | this `verdict` |
     | ---- | ---- |
     | missing contrast file | `ambiguous` |
     | `justified` | `distinct` |
     | `over_fine` | `similar` |
     | `inconclusive` | `inconclusive` |
   - `distinct` = keep-apart evidence (maps from pair `justified`).
   - `similar` = merge evidence (maps from pair `over_fine`).
   - `inconclusive` = this edge cannot decide keep vs merge — same meaning as
     pair `separation_call: inconclusive` (unusable / contradictory evidence).
     Not a missing file (`ambiguous`) and not a neighborhood_separation value.
   - `ambiguous` = missing card, not a behavior judgment.
3. Read the PATTERN of neighbor verdicts (not “does one edge match the medoid”).
   A collision-boundary cluster often shows mixed calls: some `distinct`
   (stay-behind vs overlap / go-through) and some `similar` (same pass family,
   outcome / late clearance only). That pattern is the intended product.
   This is the expected signature when whole-trajectory MFPCA+HDBSCAN has
   grouped similar trajectories across a behavior boundary: do not relabel the
   boundary cases merely to make them agree with the medoid.
4. Roll up `neighborhood_separation`:
   - `well_separated` — neighbors mostly `distinct`, and those distinct edges
     tell the SAME geometry family as each other (all stay-behind, or all
     go-through).
   - `merge_candidates` — neighbors mostly `similar` (same family + outcome).
   - `needs_finer_split` — this cluster’s own boundary sides mix families
     (yield-family on one neighbor, pass-family on another), OR neighbors
     DISAGREE with each other: at least one `distinct` AND at least one
     `similar`. Whole-trajectory clustering glued two behaviors into one
     collision-boundary cluster. Do NOT use this merely because one boundary
     trial ≠ the medoid string.
   - `ambiguous` — missing medoid_trial.yaml / contrast.yaml or conflicting evidence.
5. `distinct_from_neighbors` is computed by the pipeline from neighbor_comparison
   (true only if every verdict is `distinct`) — do not invent it.
   Never write pair words (`justified`, `over_fine`) or `inconclusive` on
   `neighborhood_separation`.
6. Label (deterministic, closed vocabulary — do NOT freehand prose): look up the
   medoid's `interaction_resolution` (preferred) or `primary_motive` in
   common_sense's Resolution class table to get PASS / YIELD / OTHER, pick at most
   one Modifier from `control_response` / the medoid's decision_timeline
   intensity/timing, then append the Collision / Near-miss suffix using this
   cluster's collision-rate dominance (numeric digest / medoid outcome). Compose
   `label` ONLY from the building blocks in common_sense's "Cluster label building
   blocks" so names match the standard vocabulary — e.g. "Pass-First",
   "Smooth Pass", "Pass-Slowdown", "Proactive Yield", "Late Yield", "Yield",
   "Yield-Stop Collision", "Brake Rear-end", "Cut-in Collision". If resolution
   maps to OTHER and the cluster is collision-dominant, name the vehicle
   (e.g. "CuttingIn Collision", "Oncoming Collision", "Parking Collision").
</Mandatory Workflow & Chain Of Thought>
