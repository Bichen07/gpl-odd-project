# results/

Generated analysis outputs (local only — not committed; see root `.gitignore`).

## Layout

```
results/
├── map/                                  # shared map assets
└── batch<id>/
    └── <k>_cluster_s=<silhouette>/       # one candidate partition
        ├── clustering/selectedClusteringResult.json
        ├── manifest.json
        ├── cluster<N>/
        ├── parameter_space_pairs/cA-cB/  # matched initial-condition pairs
        ├── trajectory_projection_pairs/  # closest MFPCA/FPC trajectories
        ├── cross_cluster/{input,output}/ # selection report and optional LLM verdict
        └── analysis/
            ├── quality/                  # composite quality score
            ├── odd/{input,output,snapshots}/
            ├── metadata/                 # provenance
            └── logs/                     # run logs and stage summaries
```

## How to generate

```bash
conda activate analyzer

# CREATE complete LLM dataset pack (auto map ensure)
python3 app/analyzer/src/dataset_builder.py --batch-id 2 --k 4

# Map assets only
python3 app/analyzer/src/dataset_builder.py --batch-id 2 --map-only

# REBUILD BEV/labels in an existing pack
python3 app/analyzer/src/dataset_builder.py --batch-id 2 --from-run results/batch2/4_cluster

# Paper case studies (Path A): export labels from local zip, then rebuild BEV
python3 scripts/paper_casestudies/export_clusters_to_results.py
python3 app/analyzer/src/dataset_builder.py --batch-id 9 --k 4 \
  --analysis-zip data/paper_casestudies/case2/casestudy2.zip \
  --from-run results/batch9/4_cluster
```

See `scripts/paper_casestudies/README.md` for mirroring senior Payload offline.

| Output | Command |

## Why one run contains many JSON files

One folder such as `batch8/6_cluster_s=0.6113/` is a working directory for
multiple stages. The files are not duplicate copies of one result:

1. The analyzer creates the clustering and per-cluster artifacts.
2. The medoid, pair, and summary products create narrative YAML cards.
3. Cross-cluster evaluation reads those cards and creates one whole-partition
   LLM result.
4. The optional ODD pipeline exports all trial parameters, finds parameter
   boundaries, fits readable rules, joins boundary evidence, and prepares a
   separate chat knowledge base.

The run artifacts are therefore a mixture of source metadata, rule outputs,
LLM outputs, and caches. They should not all be merged into one file because
they have different owners, rerun times, consumers, and evidence semantics.

## Organized artifact inventory

### Core clustering and cross-cluster analysis

- **`manifest.json` — metadata/index; generated by the analyzer.** Records the
  run, cluster count, medoid references, and trajectory-projection boundary
  pairs. The dashboard and cross-cluster evaluator use it to discover
  boundary descriptions. It is not itself an LLM judgment.
- **`clustering/selectedClusteringResult.json` — analyzer source result.**
  Contains the selected clustering labels and clustering scores used to map
  trials to clusters. It is read by dataset-building/export code and is not
  sent directly to the LLM.
- **`cross_cluster/input/cluster_selection_eval.json` — deterministic selection evaluation.**
  `cluster_selection_eval.py` reads `cluster.json`, medoid motive fields, and
  parameter-space `pair.json` metadata to calculate outcome purity, motive
  distinctness, pair decisiveness, merge signals, and `selection_score`.
  There is no new LLM call. Its compact findings digest is later supplied to
  the cross-cluster LLM.
- **`cross_cluster/output/cross_cluster_eval.json` — final whole-partition LLM output.**
  `cross_cluster_evaluator.py` builds one prompt from cluster summaries,
  medoid cards, Parameter-space contrast cards, neighbor rollups, boundary
  descriptions, and the deterministic selection digest. The configured LLM
  generates behavioral separation, boundary clarity, notes, archetypes,
  merge/split candidates, and a recommendation. This is an LLM output, not a
  rule score.
- **`analysis/quality/clustering_quality.json` — deterministic ranking plus optional LLM blend.**
  `clustering_quality_scorer.py` calculates `rule_score` from silhouette,
  collision-rate spread, TTC spread, parameter non-overlap, and
  intra-cluster consistency. If a complete `cross_cluster_eval.json` exists,
  it calculates `llm_score` and blends the values into `final_score`. It does
  not make a new LLM call.
- **`analysis/logs/split_analysis_summary.json` — orchestration ledger.** Written by
  `split_analysis.py` with paths/statuses for products run in that invocation.
  It is useful for audit/debugging but is not analysis evidence and is not
  sent to an LLM.

**Version note:** if an existing `cluster_selection_eval.json` contains extra
fields such as `boundary_behavior_consistency`, those fields belong to an
older experimental report schema. The current evaluator writes the four
components documented above. Regenerate the selection report before comparing
scores across runs.

The YAML cards under `cluster<N>/output/` and
`parameter_space_pairs/cA-cB/output/` are also important: they are the earlier
LLM-produced medoid, per-cluster summary, and pair-contrast evidence consumed
by `cross_cluster_eval.json`. They are not redundant with the final
whole-partition result.

### Optional ODD boundary/rules/chat pipeline

These files belong to S2–S5, which is separate from the cross-cluster
partition verdict:

- **`analysis/odd/output/odd_boundary_export.json` — latest S2 boundary export.** Generated by
  `odd_export.py` or the Dashboard Export ODD boundary action. It contains
  min–max-normalized scenario-parameter kNN collision boundaries, cluster
  boundaries, trial IDs, and edges. It is deterministic and has no LLM call.
  S4, the Report panel, and the briefing builder read it.
- **`analysis/odd/input/odd_all_trials.json` — S2 complete trial table.** Contains every trial’s
  scenario parameters, collision KPI result, and cluster label. It is the
  training input for S3 CART in `odd_parameter_rules.py`; it is not sent
  directly to an LLM. It is larger because S3 must learn from all trials, not
  only boundary trials.
- **`analysis/odd/snapshots/odd_boundary_export.kNN10.json` — S2 parameter snapshot.** It preserves
  the result for a specific kNN value so a later export with another kNN does
  not erase that sensitivity point. In the inspected run it is byte-for-byte
  identical to `odd_boundary_export.json`, so it is redundant *for the current
  single-kNN state*. Keep it when comparing kNN values; otherwise it can be
  treated as a removable cache after verifying no audit requires it.
- **`analysis/odd/output/odd_parameter_rules.json` — S3 shallow CART output.** Generated by Python
  `odd_rules.py` from `odd_all_trials.json`. It contains human-readable
  parameter predicates, support, precision, and limitations. It is a
  rule-based hypothesis about sampled data, not a certified ODD and not an
  LLM result. The Report panel and the briefing builder read it.
- **`analysis/odd/output/odd_boundary_pairs_join.json` — S4 join output.** Generated by Python
  `odd_join.py` by joining S2 boundary trial IDs with
  `parameter_space_pairs/*/pair.json`. It also copies an optional
  `separation_call` from an earlier `contrast.yaml`. The join itself is
  deterministic and uses trial-ID membership, never distance comparison; it
  does not make an LLM call.
- **`analysis/odd/output/odd_chat_briefing.json` — S5a deterministic knowledge base.** Generated
  by `odd_briefing.py` from cluster cards, pair cards, selection/quality
  reports, ODD boundaries, rules, and the S4 join. It truncates and organizes
  evidence for chat. It is not an LLM judgment, but it contains summaries
  and pair explanations that were produced by earlier LLM stages.
- **`analysis/metadata/PAPER_SOURCE.json` — provenance metadata.** Written by the paper-case
  study export script. It records the paper case, source archive, batch, and
  mapping counts. It is audit metadata and is not used as an LLM prompt.

## Which files are important?

- For the **core clustering analysis**, keep `manifest.json`,
  `clustering/selectedClusteringResult.json`, the per-cluster and pair
  output cards,
  `cluster_selection_eval.json`, `cross_cluster_eval.json`, and
  `analysis/quality/clustering_quality.json`.
- For the **ODD boundary/rule workflow**, keep
-  `analysis/odd/output/odd_boundary_export.json`,
  `analysis/odd/input/odd_all_trials.json`,
  `analysis/odd/output/odd_parameter_rules.json`, and
  `analysis/odd/output/odd_boundary_pairs_join.json`.
- For **ODD chat**, keep `analysis/odd/output/odd_chat_briefing.json`; it is
  regenerable, but the
  chat endpoint expects it to exist.
- For **paper reproducibility**, keep `analysis/metadata/PAPER_SOURCE.json`.
- `analysis/logs/split_analysis_summary.json` is useful but optional. It records how a run
  was produced rather than what the model concluded.
- `analysis/odd/snapshots/odd_boundary_export.kNN<k>.json` is the clearest removable duplicate when
  it matches the latest export and no kNN sensitivity analysis is needed.

## Should the JSON files be merged?

Generally, no. Combining them would:

- mix deterministic inputs with LLM outputs;
- make independently rerunnable stages overwrite unrelated results;
- make it unclear whether a value came from rules, an earlier LLM card, or
  the final cross-cluster LLM;
- force every consumer to load a large file even when it needs one small
  artifact.

A better cleanup is to treat the folder as a staged artifact bundle:
`cross_cluster/` for partition evaluation and `analysis/` for quality, ODD,
provenance, and diagnostics.
Independently generated files remain separate because they can be regenerated
at different times.

## Implemented organized layout

The selected run `batch8/6_cluster_s=0.6113/` now uses this layout for
generated run-level artifacts:

```text
<run>/
├── manifest.json
├── clustering/selectedClusteringResult.json
├── cluster<N>/
├── parameter_space_pairs/
├── trajectory_projection_pairs/
├── cross_cluster/
│   ├── input/
│   │   └── cluster_selection_eval.json
│   └── output/
│       └── cross_cluster_eval.json
└── analysis/
    ├── quality/clustering_quality.json
    ├── odd/
    │   ├── input/odd_all_trials.json
    │   ├── output/{odd_boundary_export.json, odd_parameter_rules.json,
    │   │          odd_boundary_pairs_join.json, odd_chat_briefing.json}
    │   └── snapshots/odd_boundary_export.kNN<k>.json
    ├── metadata/PAPER_SOURCE.json
    └── logs/{split_analysis_summary.json, odd_chat_log.jsonl, *.log}
```

`cross_cluster/input/cluster_selection_eval.json` is a rule-generated
intermediate consumed by the optional final cross-cluster LLM; it is not an
LLM output.
`cross_cluster/output/cross_cluster_eval.json` is the final LLM result.
`analysis/quality/clustering_quality.json` is the rule score plus the optional blend of
that LLM result, so it has its own directory rather than being hidden inside
the LLM output directory. The root-level source directories contain the cards and
clustering data that are read by both pipelines; they should not be copied
into multiple input folders.

The Python pipeline and Dashboard API use the organized paths for new writes.
Readers first check the new paths and then fall back to the previous
`source/`, previous organized, or historical root-level paths, so older runs
continue to work. No LLM analysis is run by the migration itself.
