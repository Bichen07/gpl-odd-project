# Meeting record: 16 and 20 October

## Part I — Meeting context, current state, and research direction

### Current system state

- The current action extractor and context builder already turn individual longitudinal motion, lane changes, turning, and pairwise distance/angle into LLM input. The implemented behavior vocabulary, its timestamps, and its limitations still need to be documented.
- The Replayer currently displays a timestamped text box in the upper-right corner. It does not immediately show which actor is being described or which vehicle/obstacle triggered the action. The required direction is actor-local, time-aligned annotation with inspectable evidence.
- The present LLM role should grow from one-way result description into a constrained analysis assistant. It may retrieve evidence and invoke registered analysis tools, suggest alternative interpretations, and guide the next step; a human remains responsible for approval and conclusions.

### Collision and responsibility-analysis framing

- A collision review must keep four layers separate: recorded observation, deterministic physical calculation, model-assisted inference, and legal responsibility. The prototype supports the first three and may flag candidate issues; it must not claim a legal fault verdict.
- A useful case review needs first possible perception time, vehicle capability limits, road context, and a full response-time budget. Missing payload fields must be declared as limitations or clearly labelled assumptions.
- Every LLM explanation must agree with measured data, units, Newtonian motion, and explicit assumptions. VSCC/type-approval material and NHTSA crash information are background references, not evidence that replaces project data.

### Human–AI interaction and research direction

- The target interaction is mixed-initiative Q&A: the system answers, suggests evidence checks or analyses, discloses unsupported requests, and uses only auditable registered tools.
- The system must publish structured semantics for its visual views and operations so an AI can act from facts, not only from screenshots or VLM interpretation.
- The planned research contribution connects single-case collision analysis, exploratory ODD-boundary analysis, cross-scenario comparison, and a demonstrable human–AI collaborative workflow. Interface and model choices require empirical evaluation.

### 16 October — Replayer, evidence, and collision analysis

1. **R01 — Document and extend the existing action vocabulary.** The system shall document what the current action extractor and context builder already derive for each actor—longitudinal acceleration/deceleration, lane changes, turning, and relative distance/angle between two vehicles—and identify the missing vehicle–vehicle and vehicle–environment behaviors. The derived facts must be usable as LLM input with their source timestamps.

   > **Original Chinese note:** 「針對行為多講一點，確認能解釋的行為有哪些? 個體加速減速轉彎，或是車輛互動、環境互動? 目前是action extractor, context builder 會處理個別車輛的加減速度(縱向)、車道切換、轉彎(橫向)、也能將兩車的相對距離、角度轉換成文字，變成給LLM 的 input。」

2. **R02 — Make Replayer explanations actor- and cause-specific.** Replace the single timestamp text box in the upper-right corner with time-aligned annotations placed next to the relevant vehicle or obstacle. Each annotation shall state the observed behavior (for example, accelerating, braking, turning, or imminent collision) and, when evidence supports it, the interacting vehicle or obstacle that explains the behavior.

   > **Original Chinese note:** 「增加文字搭配影片，像是replyer 現在車輛旁，可以直接標示是哪一個車輛，像正在加速 減速 即將碰撞等等，並且可能是因為哪台車或路障才會加速或減速等等。目前replayer是 time stamp 一個 text box在右上角顯示，這樣的視覺畫不直覺，使用者沒辦法一瞬間知道這段文字在說誰的行為。」

3. **R03 — Balance qualitative narration and quantitative evidence.** Narratives shall be concise, but every interpretation must be inspectable through contextual measurements such as speed, acceleration, distance, relative angle, and time-to-collision. The interface shall use local road/scenario context rather than treating one absolute speed as universally “fast.”

   > **Original Chinese note:** 「怎麼在質化量化間平衡? 要多給數據像是速度加速度(但為讓使用者看到一堆數據)? 或是文字多(但數據少怎麼知道誰快誰慢? 高速公路的快跟郊區的速度快會一樣快嗎? ANS 不會)」

4. **R04 — Provide a constrained analysis agent for engineering questions.** The agent may retrieve approved evidence and run registered analysis tools to support vehicle dynamics, physics, collision avoidability, road context, and candidate responsibility analysis. It must not independently make unsupported legal conclusions or control arbitrary software.

   > **Original Chinese note:** 「能不能透過agent去操作? 考慮汽車動力學、物理學、責任歸屬判斷(自駕車有沒有能力避免這個碰撞)，是誰的責任、道路問題? 責任歸屬。」

5. **R05 — Establish the first-perception timeline.** For every collision case, report the first time the AV could perceive, track, and react to the other actor. If perception data are unavailable, state that limitation explicitly rather than inferring it.

   > **Original Chinese note:** 「能不能知道什麼時候自駕車第一次看到其他車輛，由此判斷造責？」

6. **R06 — Separate physical avoidability from candidate system responsibility.** Evaluate whether a sudden vehicle or pedestrian entry was physically avoidable after detection. An unavoidable event may lower a candidate AV contribution; an avoidable event where the AV did not brake or selected acceleration instead must be flagged for engineering review. This is an engineering assessment, not a legal verdict.

   > **Original Chinese note:** 「若自駕車根本沒機會接受到突如其來衝出的車輛或行人，或許沒辦法避免碰撞，這樣的碰撞或許自駕車責任較低。」「相反，若自架系統能力允許，但卻未阻止碰撞發生，那可能是自駕系統的問題。像是為甚麼不煞車? 而採取加速的判斷? model黑盒子(軟體)需要被檢視。」

7. **R07 — Model vehicle capability and improvement paths explicitly.** The capability calculation shall consider braking, longitudinal acceleration, lateral/steering capability, and response delay. It shall distinguish current hardware/physical limits from possible future improvements; assumptions must be visible and replaceable when measured values become available.

   > **Original Chinese note:** 「可以考慮煞車能力、加速能力。超過自駕車能力範圍的話，碰撞可能沒辦法避免。代表可能不是”目前”自駕車系統的問題…但可以改進目前自駕車的物理能力，例如怎麼在更短的時間內做出反應，這可能牽涉到物理(硬體)設備更新。」

8. **R08 — Include road context and dynamics without overclaiming responsibility.** The analysis shall display relevant grade, right-of-way, and longitudinal/lateral dynamic limits. It may identify how downhill/uphill context changes an engineering interpretation, but it shall label responsibility statements as hypotheses requiring human review.

   > **Original Chinese note:** 「或是 上坡路權大 自駕車因為下坡撞到人，可能責任大。自駕責任比較大? 那怎麼改善，車輛動態物理極限。直線加速度、轉向加速度。有些自駕車就是無法避免。」

9. **R09 — Ground every LLM explanation in physics and recorded evidence.** The LLM shall receive structured measurements, units, and assumptions and must not produce claims that conflict with Newtonian motion or available data. It shall distinguish observation, calculation, inference, and uncertainty.

   > **Original Chinese note:** 「請LLM判斷的時候要符合牛頓定律。物理常規 要根據資料」

10. **R10 — Evaluate emergency braking and end-to-end response time.** Define the required input components for a braking analysis: physical sensing/receipt, model input-to-output delay, actuation delay, and vehicle response. Any comparison with human response or braking expectations must cite the selected benchmark and avoid unsupported universal thresholds.

    > **Original Chinese note:** 「緊急煞車要到多少加速度以上才合理? 總共處理時間 = 各項加總(物理接受、model input 至 output，設備在做出反應)，反應速度不能比人類差。」

11. **R11 — Expand LLM involvement from explanation to accountable analytical assistance.** The LLM/agent shall propose evidence-backed collision explanations, candidate AV weaknesses, alternative views, and registered re-draw/re-filter/re-interpret actions. Its proposals remain review prompts for engineers, not final facts.

    > **Original Chinese note:** 「在目前整個流程中，LLM涉入範圍算小，LLM對於原因分析使用範圍太小。可以嘗試多融入agent在系統中，讓LLM協助分析，協助推導碰撞原因、肇責分析，即使不一定正確，但可以提醒工程師注意哪些情況可能是自駕車問題，讓LLM使用更廣，甚至重新繪製徒刑，重新解讀，加入不同於目前系統的分析方式。」

12. **R12 — Research regulatory and crash-data context as cited background.** Review VSCC vehicle-safety/type-approval material and NHTSA crash reports or databases to frame requirements and examples. Keep external evidence separate from facts measured in the project’s own scenarios.

    > **Original Chinese note:** 「vscc 車輛安審 型式認證」「交通事故資料庫? NHTSA 事故報告」

## 20 October — Human–AI interaction and Q&A

13. **R13 — Use mixed-initiative, recursive Q&A.** The interface shall support a bounded conversation: after answering, it may offer relevant next questions, evidence checks, or analyses based on the current state rather than only waiting for another one-shot user query.

    > **Original Chinese note:** 「介面能不能設計成遞迴式，在使用中跟使用者互動，不是只是被動接受只等使用者問AQ問題，然後AI回復。」

14. **R14 — Route general and project-grounded questions differently.** The Q&A design shall distinguish questions answerable from loaded project data, questions about the interface/method, and general-domain questions. The response shall identify its evidence basis and limitations, informed by visual-analytics interaction literature.

    > **Original Chinese note:** 「Q&A 可不可以直接問general的問題。如何去設計? 參考其他視覺化系統論文」

15. **R15 — Evaluate visualization-capable model choices empirically.** Compare current general models, VLM-assisted alternatives, and any visualization-specialized candidate on the same grounded tasks. Do not assume that a model marketed for visualization produces better analysis without evidence.

    > **Original Chinese note:** 「有沒有特定的模型，而不是一般的模型像是chatGPT等等，而是針對視覺化去做優化，產生更好的分析與解讀的模型。」

16. **R16 — Make supported scope and out-of-scope handling explicit.** The system shall state what data, methods, tool permissions, and questions it can support. If a question exceeds the validated scope, it shall say so clearly and offer a supported alternative instead of fabricating an answer.

    > **Original Chinese note:** 「確認我們系統能處理的問題範疇。像是有些不在我們既有分析的範圍，那怎麼處理? AI能否明確告知超出系統設計範圍?」

17. **R17 — Let the agent use only registered, auditable tools.** Where a requested task is supported, the agent may read approved files and invoke validated analytical tools rather than requiring the user to operate every tool manually. Tool arguments, results, provenance, cost, and failures must be visible; state-changing actions require confirmation.

    > **Original Chinese note:** 「確認特定問題，我們目前系統、工具處理得到? 如果處理得了，能不能讓AI去使用我們的工具，不用我們自己去操作。類似agent的概念，讓AI去跑分析、讀取各種檔案等等。AI能不能善用工具。」

18. **R18 — Define a human-controlled interaction policy.** Specify which analyses the AI may propose, which tools it may run automatically, and which actions require user confirmation. The purpose is useful assistance with retained user authority, not unrestricted interface control.

    > **Original Chinese note:** 「互動模式這類介面怎麼設計? 是否允許AI去做分析，是否允許AI去操作我們的工具。」

19. **R19 — Benchmark relevant visual-analytics interfaces and patterns.** Study mature visual-analytics platforms, including commercial-data platforms where their interaction patterns transfer, and document which patterns are adapted rather than copied. Evaluate them against the project’s scenario-analysis needs.

    > **Original Chinese note:** 「可以參考比較大的視覺化平台。也許用在商業資料，不是車輛資料，但互動設計可以參考。 目前最強的是哪個介面? 可以去參考。」

20. **R20 — Frame the system as human–AI collaborative analysis.** Move beyond plain result interpretation: the system shall guide users through evidence, propose useful next analytical steps, and leave decisions, claims, and tool approvals to the human analyst.

    > **Original Chinese note:** 「human AI 合作視覺化 analysis 人機協作分析。」「從單純結果解讀，到引導使用者去分析，提供更多建議。」

21. **R21 — Publish machine-readable visualization semantics.** Expose structured descriptions of heatmaps, parameter spaces, filters, Replayer state, encodings, units, selected records, and permitted operations. A VLM may assist as secondary evidence, but it must not be the sole way for an AI to understand or operate the system.

    > **Original Chinese note:** 「怎麼將系統轉化成符合事實的文字描述，讓AI更可以操作或是理解，了解這些內容的意義。VLM 足夠? 直接看懂我們的系統? 像是 heatmap, parameter space, filter, replayer 等意義? 並且有辦法操作? 還是需要透過甚麼方式轉換成文字，才能讓AI操縱?」

22. **R22 — Treat voice as an optional later input channel.** If voice input is added, it shall create the same visible transcript, extracted intent, proposed tool plan, confirmation gates, and evidence trace as typed input.

    > **Original Chinese note:** 「或甚至導入語音輸入。讓使用者可以直接語音對話」

## 20 October — ODD and scenario analysis

23. **R23 — Support ODD-boundary exploration in native parameter spaces.** For a scenario family, represent sampled collision points as lines, surfaces, or higher-dimensional structures when justified by the data. Label the output as exploratory ODD analysis rather than a certified boundary.

    > **Original Chinese note:** 「可以做ODD分析—> 線或面的分析(很多個碰撞點 在高維空間中連成的面)」

24. **R24 — Support single-case collision/avoidability analysis.** Use the evidence, perception timeline, and capability calculation to analyze one collision situation and identify candidate causes and engineering improvements.

    > **Original Chinese note:** 「也可以做車禍肇責分析—> 單點分析(單個碰撞情境分析)」

25. **R25 — Define paper demonstration cases.** The final paper demo shall show several concrete scenarios and explain the analytical question, evidence, visual/agent interaction, result, limitation, and practical application for each.

    > **Original Chinese note:** 「最後論文要能夠demo，展示幾個情境，解釋分析以及應用。」

26. **R26 — Compare scenarios without pretending different dimensions are identical.** Retain each scenario’s native ODD dimensions (for example, speed and distance for one approaching vehicle versus four inputs for two vehicles). Define canonical comparable features where possible, display missingness/non-comparability, and evaluate whether cross-scenario conclusions are valid.

    > **Original Chinese note:** 「大規模，怎麼跨越scenario，像是同樣都是十字路口，如果來車數量不一樣，那怎麼分析? 這樣ODD 維度就不一樣，舉例一台來車可以有初始速度與距離兩個軸當作輸入變因，如果兩台車的話就會有四個軸，這樣的ODD boundary就會是四維的，當考慮不同情境，就會有不同維度的ODD空間。該怎麼處理? 能夠跨場景分析嗎? 可不可以跨越不同scenario分析?」

27. **R27 — Reuse suitable existing methods and make all available data analyzable.** Survey reusable systems, ChatGPT-style visualization capabilities, and large VLM options; adapt a suitable method only after checking fit. Build an evidence bundle from the existing data so that the AI can perform complete, grounded visual analysis without inventing fields that are not present.

    > **Original Chinese note:** 「若找到合適系統或方法，可以先搬過來，再做調整。」「或是從chatGPT這類工具，若有提供視覺化功能的話，能不能拿來用? 現成還有甚麼工具適合使用? 大型VLM?」「既有的資料，怎麼讓AI去完整分析，去做完整視覺化分析?」

## Phase A implementation outcome — data truth and capability analysis

**Coverage:** R05–R10 and R24. This section records implementation facts and known limits; it does not make a legal responsibility, type-approval, or certification claim.

### Implemented evidence flow

1. The scenario sampler now snapshots a collision event only when its current observation has positive `time` and `esminiSeconds`. It records the collision partner, observation index, `source: sampler_collision_callback`, and `timeStatus: recorded`; it does not store a zero timestamp as a recorded collision time.
2. After Payload accepts the ordered observation batch, the sampler checks the returned observation count, resolves each event to the returned observation ID, deduplicates the event list, and PATCHes it to the trial. An invalid response order/count prevents event linking rather than attaching an event to an incorrect frame.
3. A trial event now carries its observation relationship, source, and time status. The Analyzer accepts a persisted event as ground truth only when it is recorded, observation-linked, and has a positive time. Otherwise it falls back to its existing deterministic polygon-clearance resolver and labels that contact time as `derived`.
4. The Analyzer writes `processed/capability.yaml` beside `action.yaml`. The card contains input status, unit, source/provenance where available, collision source, prohibited-claim markers, and an engineering-only verdict. The Replayer/LLM integration is deferred to later phases.

### Data-status rule now enforced

- `recorded`: directly logged by the trial, such as an observation-linked collision callback.
- `derived`: deterministically calculated from recorded trajectory/event data, such as the polygon collision fallback.
- `configured`: tied to a versioned, explicitly selected runtime configuration only.
- `assumed`: permitted only in explicit synthetic fixtures; not emitted as a real-trial fact by Phase A.
- `unavailable`: required evidence is missing. Real cards default to `insufficient_data` when perception or physical capability provenance is absent.

### Current blockers retained as unavailable

1. **First perception:** no sensor-detection event is recorded, so the system does not use first-in-range as a proxy.
2. **End-to-end response time:** RSS `responseTime` is a configuration value, not measured sensing, model, and actuator latency for a trial.
3. **Emergency braking and lateral capability:** RSS, Pacifica, and catalog files are hashed for provenance, but historical trials do not identify their runtime vehicle/controller binding. The Analyzer never selects the first catalog vehicle as a fallback.
4. **Road grade, friction, right-of-way, and human-response comparison:** no reliable per-trial source is currently recorded.

### Verification status

- Pure sampler, capability schema/source, and deterministic-analysis tests pass, including late cut-in, early-visible/no-brake, braking-limit disagreement, and missing-lane cases.
- Payload types were regenerated and the Phase A schema contract test passes.
- The complete Payload integration suite still requires the project PostgreSQL service (`postgres`); it could not run in the current environment because that hostname was unavailable. This is an environment blocker, not evidence that the unrun database integration has passed.
