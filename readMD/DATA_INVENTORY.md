> **Purpose:** Explain where data lives, why `alldatasets/` and `simulation/.cache/` look different, and how to run sampling → simulation → cluster interpretation without surprises.

## Executive summary

| Question | Short answer |
|----------|--------------|
| Where do simulation results go? | **`simulation/ros/.cache/scenario_search/records/`** (esmini `.dat` → `.csv`, plus `scenario_<N>.xosc`) |
| What is `alldatasets/dataset<N>/`? | **Analyzer exports** from the lab (clustering, embeddings, collision flags, Payload-derived trajectories) — **not** a substitute for esmini CSVs |

| Why does `build_llm_dataset.sh dataset3 4` fail? | Cluster medoids need `esmini_3_*.csv` files that **do not exist locally** (you only have indices 0–4; clustering needs indices ~869+) |

| Can I cluster now and re-cluster when more trials finish? | **Yes** — each **Analysis** run reads **all** Payload trials for that batch. Prior **Save** is a snapshot; re-run **Analysis** after new sims. |

┌─────────────────────────────────────────────────────────────────────────┐

│    records/scenario_<index>.xosc                                        │

└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  LAYER C — results/              (your LLM pipeline output)             │

**Rule of thumb:** `alldatasets/` answers *which trial belongs to which cluster*; `simulation/.../records/` answers *what actually happened frame-by-frame in esmini*.

## 2. FAQ — common data-flow questions

### Q1. Does simulation (lab or local) write `esmini_<batch>_<index>.csv`?

**Yes.** Both lab and local simulation use the same path inside the ROS workspace:

| Environment | Path on disk |
|-------------|--------------|
| Inside Docker | `/project/mmsl_simulation/.cache/scenario_search/records/` |
| Your repo (bind-mount) | `simulation/ros/.cache/scenario_search/records/` |

**Per-trial sequence** (`single_parameterized_scenario_search.py`):

```text
1. esmini records  →  records/esmini_<batch>_<trial_index>.dat
2. dat2csv.py      →  records/esmini_<batch>_<trial_index>.csv   (same basename)
3. optional        →  records/scenario_<trial_index>.xosc
4. observations    →  Payload CMS (not the same file as CSV)
```

The `<trial_index>` is the sampler’s loop index (`current_trial_index`), **not** the Payload trial_id. Payload trial_id = `trial_id_base + trial_index` (see `dataset_config.py`).

Mission Control (`app/simulation/src/orchestrator.py`) polls the same folder for new `esmini_<batch>_*.csv` after each trial.

### Q2b. How to run MFPCA + HDBSCAN from the Dashboard (and why **Analysis** can look like it does nothing)

**Where it runs:** MFPCA and HDBSCAN are **not** separate CLI tools you run by hand in normal workflow. Both run inside the **Analyzer** service (`app/analyzer`, port **9010**). The **Dashboard** only triggers them and visualizes results.

```text
Dashboard Explore  →  POST http://localhost:9010/trajectory_analysis
                         ├─ fetch trials + observations from Payload
                         ├─ MFPCA on ego time series (per duration mode)
                         ├─ UMAP → 2D embeddings
                         └─ HDBSCAN grid (one result per "task" in the request)
```

**UI path** (`http://localhost:3000/batch/<batch_id>` → **Explore** tab):

| Panel | What you do |
|-------|-------------|
| **Saves** → **Create New** → **Analysis** | Starts MFPCA + full HDBSCAN parameter grid (~**488** tasks by default — see `Saves/index.tsx`). Button shows a spinner while waiting. |
| **Clustering Selection** | After Analysis finishes, compare runs (silhouette, cluster count) and pick one → **Use Selection**. |
| **Parameter Space** plot | UMAP / MFPCA scatter colored by selected clusters (updates after selection). |
| **Saves** → **Create New** → **save** | Uploads the in-memory analysis JSON to Payload **Documents** (only works **after** a successful Analysis). |

**Prerequisites (all must be true):**

1. **Dev stack running** — `./scripts/start_dev_stack.sh` (or at least Analyzer on **9010** + Dashboard on **3000**).
2. **Analyzer can reach Payload** — copy `app/analyzer/.env.example` → `app/analyzer/.env` and set the **same** `PAYLOAD_API` / `PAYLOAD_API_KEY` as `app/dashboard/.env`.  
   If Analyzer points at `http://localhost:3020` but Payload is on the lab host (`140.113.208.174:3020`), Analysis returns empty or errors with **no toast** in the UI.
3. **Trials exist in Payload** for that batch (observations uploaded by simulation — CSVs on disk alone are not enough for clustering).
4. **Browser** — open DevTools → **Network** → watch `POST …/trajectory_analysis` (can run **15–60+ minutes** for ~200 trials × 488 HDBSCAN tasks; longer on CPU).

**Why it seems like “nothing happened”:**

| Symptom | Likely cause |
|---------|----------------|
| Spinner stops, plots unchanged | Request failed or returned `null`; errors only in browser **Console** (UI swallows failures). Check Network tab + `logs/dev_stack/analyzer.log`. |
| Spinner runs a long time | Normal — default grid is large. For a quick test, use the **curl** one-task example in **§10 Phase D** instead of the full Dashboard grid. |
| **save** opens modal but upload fails | No successful Analysis in Redux yet, or Payload document upload error. Run **Analysis** first; wait until **Clustering Selection** lists results. |
| Analyzer log shows `localhost:3020` | Fix `app/analyzer/.env` to lab Payload URL, restart Analyzer. |

**Incremental runs (200 trials now, more later):**

- **Analysis** always loads **every trial** currently linked to the batch in Payload — not only new CSVs.
- You **can** cluster ~200 trials now, pick a clustering in **Clustering Selection**, and use the Explore views immediately.
- When simulation adds trials (e.g. 203 → 500 → 3000), click **Analysis** again. That recomputes MFPCA + HDBSCAN on the **full** set; labels and embeddings will change.
- A previous **Save** (Payload document or manual `alldatasets/` export) is a **frozen snapshot** — it does not auto-update. Re-save after re-analysis if you want a new bundle.
- For the **LLM pipeline** (`build_llm_dataset.sh`), you still need matching `esmini_<batch>_<index>.csv` files locally for medoid trials — clustering JSON alone is not enough (see **§4**).

**Optional — Analyzer API without Dashboard** (single HDBSCAN task, faster smoke test):

```bash
curl -X POST http://localhost:9010/trajectory_analysis \
  -H "Content-Type: application/json" \
  -d '{"batchIds":["3"],"framePeriod":0.1,"tasks":[{"method":"hdbscan+mfpca","nClusters":0,"minClusterSize":20,"minSamples":3,"clusterSelectionEpsilon":1.5,"clusterSelectionMethod":"eom"}]}'
```

Replace `"3"` with your Payload batch id. Response shape matches what Dashboard stores in Redux (`mfpca`, `trials`, clustering results per ego).

### Q3. Can we rebuild esmini CSV from `trajectories.json`?

**Not faithfully.** You can write a **degraded adapter** (x/y/BEV only); you cannot recover full esmini ground truth.

**What `trajectories.json` actually contains** (checked on dataset3 trial `13060`):

```json
{
  "13060": {
    "time": [0, 0.1, 0.2, ...],           // ~207 samples (~10 Hz)
    "trajectory": {
      "Ego": [
        {"x": 588.9, "y": 167.6, "yaw": 5.5, "width": 0, "length": 0,
         "s": 0, "roadId": 0, "s_ratio": 0.0},
        ...
      ],
      "Parking": [ ... same shape, roadId: 0 ... ]
    }
  }
}
```

**Compared to real `esmini_3_*.csv`:**

| Field | esmini CSV | trajectories.json |
|-------|------------|-------------------|
| `x`, `y`, `h` (yaw) | ✅ | ✅ |
| `speed` | ✅ | ❌ missing |
| `roadId` | ✅ correct (all agents) | ❌ **always 0** (even Ego) |
| `laneId` | ✅ | ❌ missing |
| `offset`, `t`, `s` | ✅ | ❌ `s` always 0 |
| `width`, `length` | ✅ from esmini | ❌ 0 |
| Temporal density | ~100 Hz raw, dense | ~10 Hz, dashboard-oriented |
| All agents per timestamp | ✅ aligned rows | ✅ per-agent lists |

**Why roadId is zero:** `trajectories.json` is built from **Payload observations** (and analyzer replayer format), not from the esmini CSV. The export path drops or never had reliable lane/road fields for the bundled JSON (see `controller.py` replayer block ~1587–1626).

**Impact on cluster interpretation pipeline:**

| Step | Works from trajectories.json alone? |
|------|-------------------------------------|
| BEV map + agent boxes (x/y) | ⚠️ Partial — could adapt `tier2_renderer` |
| Road highlight in BEV | ❌ needs `roadId` → use spatial fallback |
| Rule-based `action.yaml` (junction enter/exit) | ❌ needs `roadId` + `JunctionRoads` |
| `description.txt` | ❌ degraded without actions |
| LLM interpretation quality | ❌ poor without BEV + actions |

**Practical options (best → worst):**

1. **Sync esmini CSVs from lab** (recommended) — same trials as clustering, full quality.
2. **Download from Payload** — trials may have `esminiCsv` attachment; script `simulation/ros/src/scenario_search/script/dat2csv.py` shows the API pattern.
3. **Degraded adapter (future)** — new code path: `trajectories.json` → synthetic CSV with XODR spatial `roadId` assignment; BEV ok, actions noisy. Not implemented today.
4. **Do not** pretend `trajectories.json` is interchangeable with esmini CSV.

### Q4. Can we interpret clusters from `selectedClusteringResult_4Clusters.json` without resimulation?

**Clarification (important):** Clustering **labels** and **trial IDs** are reusable without resimulation. **Cluster interpretation** (BEV, actions, LLM) still needs **raw esmini CSV** for at least one trial per cluster (usually the medoid). If those CSVs are missing locally — as with dataset3 today — you have cluster IDs but **cannot run the full analysis pipeline**.

| What you have without local CSV | What you can do | What you cannot do |
|--------------------------------|-----------------|---------------------|
| `selectedClusteringResult_4Clusters.json` | Know trial → cluster; dashboard UMAP plots | BEV, `action.yaml`, full LLM interpret |
| `clustering.json` | Pick medoid trial IDs mathematically | Load medoid trajectory without CSV |
| `collision.json` | Collision rate per trial | — |
| `trajectories.json` | Rough x/y replay in dashboard | Reliable roadId / actions (fields are lossy) |

**You do not need to re-run simulation, MFPCA, or HDBSCAN** if senior’s clustering bundle is kept — but you **do** need to **obtain the esmini CSV files** that correspond to the medoid trial IDs (sync from lab or Payload), unless you only run a smoke test with `--trials` on the few CSVs you have.

| Artifact | Re-use as-is? | When to recompute |
|----------|---------------|-------------------|
| `selectedClusteringResult_4Clusters.json` | ✅ Yes (labels only) | Different **k** or trial set |
| `clustering.json` (embeddings) | ✅ Yes | Same — for medoid selection |
| `collision.json` | ✅ Yes | Optional LLM context |
| MFPCA / HDBSCAN | ❌ Not needed again | New trials added to batch |
| **esmini CSV for medoid trials** | ❌ **Required for interpretation** | Sync from lab / Payload |

**Interpretation workflow with existing clustering:**

```bash
# Cluster labels + medoids: already in alldatasets/dataset3/
# You only need LOCAL esmini CSV for chosen trials:

bash scripts/build_llm_dataset.sh dataset3 4
# fails today → no esmini_3_869.csv etc.

# Smoke test with the 5 local files:
bash scripts/build_llm_dataset.sh dataset3 4 --trials '3:0,3:1,3:2,3:3'

# After syncing batch-3 CSVs from lab:
bash scripts/build_llm_dataset.sh dataset3 4   # uses real medoids from JSON

bash scripts/run_cluster_interpretation.sh dataset3 4
```

**When you WOULD resimulate or re-cluster:**

| Goal | Action |
|------|--------|
| Interpret existing paper clusters (dataset3, k=4) | Sync CSVs only — **no** resim, **no** new MFPCA |
| Add 500 new trials to dataset3 | Run simulation → re-run analyzer clustering → new JSON exports |
| Try k=6 instead of k=4 | Dashboard HDBSCAN with k=6 → new `selectedClusteringResult_6Clusters.json` (embeddings can stay) |
| Fix agent roadId in Payload | Engineering fix in sampler — does not replace need for esmini CSV in LLM pipeline |

### Q5. Where does Payload store simulation results?

Payload (CMS + PostgreSQL + file uploads) stores **metadata and downsampled observations**, not the full `records/` folder tree.

| Payload collection | What it stores | On-disk files (typical) |
|--------------------|----------------|-------------------------|
| **`observations`** | Per-timestep ego + agent state (10 Hz bulk POST from sampler) | PostgreSQL rows; fields: `egoX`, `egoY`, `egoRoadId`, `egoSpeed`, `agents[]`, … |
| **`trials`** | One row per simulation run: parameters, KPI scores, link to observations | PostgreSQL |
| **`esminiDats`** | Binary esmini recording (`.dat`) per trial | `./uploads/esminiDat/` (dev) or `/data/uploads/esminiDat/` (prod docker volume) |
| **`batches`** | List of trial IDs for a campaign | PostgreSQL |
| **`documents`** | Analyzer exports (`analysis.zip`, heatmaps) | uploads volume |
| OpenDRIVE / OpenSCENARIO | Map and scenario templates | separate upload collections |

**Trial record** (`app/payload/src/collections/Trials.ts`): each trial has `esminiDat` → uploaded `.dat` file. The **converted CSV** is written on the **simulation machine** by `dat2csv.py`; it is **not** a separate Payload collection in this repo (older lab scripts may POST to `/esminiCsvs` on a different deployment).

**Lab server layout:**

```text
Payload (port 3020)
  PostgreSQL  → observations, trials, batches, KPIs
  uploads/    → esminiDats/*.dat, documents, media

Simulation container (separate from Payload DB)
  /project/mmsl_simulation/.cache/scenario_search/records/
    esmini_<batch>_<index>.csv    ← primary source for LLM pipeline
```

To interpret clusters you usually need files from the **simulation cache** (or convert/download `.dat` from Payload `esminiDats` with `dat2csv`).

### Q6. Does simulation auto-write to `simulation/ros/.cache/scenario_search/records/`?

**Yes, when simulation runs correctly with the repo bind-mount.**

`simulation/ros` is mounted into Docker as `/project/mmsl_simulation`. The scenario search node sets:

```text
SHARE_FOLDER_PATH = /project/mmsl_simulation/.cache/scenario_search
record_root_dir   = .../records/
```

After each trial: `esmini_<batch>_<trial_index>.dat` → `dat2csv` → `.csv` in the same folder.

| Condition | CSV appears in repo path? |
|-----------|---------------------------|
| Simulation runs in `sdc-bionic` with standard mount | ✅ Auto — host path `gpl-odd-project/simulation/ros/.cache/scenario_search/records/` |
| Simulation runs only on remote lab, never copied | ❌ Payload has observations; local `records/` stays empty for those trials |
| You never run simulation locally | ❌ Only whatever CSVs were copied before (1,206 total today) |
| Mission Control run | Same `records/` folder; extra logs under `.cache/mission_control/runs/` |

**Nothing syncs Payload → `records/` automatically.** Copying lab CSVs (scp/rsync) or running local simulation are the ways to populate that folder.

## 3. End-to-end data flow

### Phase A — Sampling (parameter search)

| Step | Component | Output |
|------|-----------|--------|
| 1 | Mission Control / `scenario_sampler.py` | Parameter vectors (delay, speed, …) per trial |
| 2 | Payload CMS | Trial records, scenario `.xosc` URLs, batch metadata |

Sampling **does not** write esmini CSVs. It decides *what to simulate*.

### Phase B — Simulation (esmini + ROS)

| Step | Component | Output location |
|------|-----------|-----------------|
| 1 | `single_parameterized_scenario_search.py` | Runs esmini inside Docker (`/project/mmsl_simulation`) |
| 2 | esmini recorder | `.dat` file per trial |
| 3 | `dat2csv.py` | Converts to **`records/esmini_<batch>_<trial_index>.csv`** |
| 4 | Same run | **`records/scenario_<trial_index>.xosc`** (parameterized scenario) |
| 5 | Observations posted | Payload CMS (10 Hz ego + agent states) |

**Canonical path inside container:**

```text
/project/mmsl_simulation/.cache/scenario_search/
├── hct_6.xodr
└── records/
    ├── esmini_1_0.csv
    ├── esmini_1_1.csv
    ├── scenario_0.xosc
    └── ...
```

**On your repo (bind-mount or copy):**

```text
gpl-odd-project/simulation/ros/.cache/scenario_search/records/
```

New simulations **must** land here (or be copied here) for `build_llm_dataset.sh` to work.

### Phase C — Analyzer (clustering on lab / exported bundle)

| Step | Component | Output |
|------|-----------|--------|
| 1 | `controller.py` clustering | Reads Payload observations (or bundled data) |
| 2 | MFPCA + UMAP + HDBSCAN | Writes into **`alldatasets/dataset<N>/`** |
| 3 | Export bundle | Senior zips/sends `clustering.json`, `selectedClusteringResult_*`, `trajectories.json`, etc. |

This phase produces **~3000 trial IDs per dataset** in JSON — that is the “full data” you see under `alldatasets/dataset3/`.

### Phase D — Cluster interpretation (your workstation)

```bash
# Step 0 — map assets (one-time)
python3 scripts/generate_map_tracks.py --dataset dataset3
python3 scripts/map_preprocess.py --dataset dataset3

# Steps 1–4 — needs LOCAL esmini CSV for chosen medoids
bash scripts/build_llm_dataset.sh dataset3 4

# Step 5
bash scripts/run_cluster_interpretation.sh dataset3 4
```

**What `build_llm_dataset.sh` reads:**

| Input | Path | Used for |
|-------|------|----------|
| Cluster labels | `alldatasets/<dataset>/selectedClusteringResult_<k>Clusters.json` | Which trials belong to each cluster |
| Embeddings | `alldatasets/<dataset>/clustering.json` | Medoid = trial closest to cluster centroid |
| **Trajectory ground truth** | `simulation/ros/.cache/scenario_search/records/esmini_<batch>_<index>.csv` | trajectory.csv, BEV, action.yaml |
| Map | `alldatasets/map/` + `alldatasets/resources/xodr/` | Labelling + BEV |

**What it does NOT use for trajectories:**

- `alldatasets/dataset3/trajectories.json` — Payload-derived, lossy `roadId=0` for non-Ego agents; legacy dashboard format only.

## 6. File-type reference

### a. `esmini_<batch>_<index>.csv` — **authoritative simulation recording**

- **Location:** `simulation/ros/.cache/scenario_search/records/`
- **Producer:** esmini simulation + `dat2csv.py`
- **Content:** 10 Hz, all agents, correct `roadId` / `laneId` / dimensions
- **Consumer:** `csv_roadid_loader.py` → `dataset_builder.py` → `tier2_renderer.py`, `sim_labeller.py`

### b. `alldatasets/.../clustering.json`

- Embeddings for ~3000 trials per export bundle
- Used only to **rank medoids** (distance to centroid)

### c. `alldatasets/.../selectedClusteringResult_<k>Clusters.json`

- `data`: `{ "6991": "2", ... }` — trial_id → cluster label
- Defines **which** trials belong to each cluster

### d. `alldatasets/.../trajectories.json`

- ~224 MB per dataset; `{ "13060": { "time": [...], ... }, ... }`
- Exported from Payload for dashboard / legacy analyzer paths
- **Do not use** for cluster interpretation pipeline (agent roadId unreliable)

### e. `alldatasets/.../collision.json`

- Quick trial_id → collision flag lookup

### f. OpenDRIVE + odrplot tracks

### Phase D — MFPCA + HDBSCAN → `alldatasets/` layout (Dashboard)

**Goal:** Produce the same file set senior sent for dataset1:

```text
alldatasets/<your_dataset_name>/
├── clustering.json                      # embeddings + UMAP + all clustering runs
├── selectedClusteringResult_<k>Clusters.json
├── trajectories.json
├── collision.json
└── (optional) mfpca_heatmap_cluster<N>.png
```

**Who runs what:**

| Step | Tool | Code / UI |
|------|------|-----------|
| Load trajectories from Payload | **Analyzer** | `POST /trajectory_analysis` — `app/analyzer/src/controller.py` |
| MFPCA + HDBSCAN grid | **Analyzer** (called by Dashboard) | same endpoint; tasks from Saves panel |
| Pick cluster count k | **Dashboard** | Explore → **Clustering Selection** panel |
| Run MFPCA + HDBSCAN | **Dashboard** | Explore → **Saves** → **Create New** → **Analysis** |
| Persist analysis bundle | **Dashboard** | Explore → **Saves** → **Create New** → **save** (after Analysis succeeds) |

**Dashboard steps (after Phase C has enough trials):**

1. Open Batch in Dashboard → Explore dock.
2. **Saves** → **Create New** → **Analysis**  
   - Calls `getTrajectoryAnalysis()` → analyzer `POST /trajectory_analysis`  
   - Default task grid: `hdbscan+mfpca` with `minClusterSize` 5–100, `minSamples` 3–50, `clusterSelectionEpsilon` 0–10 (see `Saves/index.tsx`).
3. Wait for UMAP / clustering grid to load (can take minutes for ~3000 trials).
4. **Clustering Selection** → compare silhouette / cluster counts → pick result closest to paper (senior used e.g. `minClusterSize: 20`, `minSamples: 3`, `clusterSelectionEpsilon: 1.5`, method `hdbscan+mfpca` for dataset1 k=4).
5. **Use Selection** / **Add** to set `selectedClusteringResult` in Redux.

**Export files to `alldatasets/` (manual today — no single CLI):**

| File | How to obtain |
|------|----------------|
| `clustering.json` | From analysis response: build `{ "embeddings": <umap or mfpca projections per trial>, "umap2DProjections": ..., "clusterings": [ all HDBSCAN results ] }`. Senior’s file has 3000 trials × 4D embeddings. Easiest: save full analysis JSON from **Saves → save** (Payload document), then extract/transform in a small script. |
| `selectedClusteringResult_<k>Clusters.json` | Copy the chosen `ClusteringResult` object from Clustering Selection (must include `task`, `scores`, `data` with `trialId → label`). Match filename to k. |
| `trajectories.json` | Download analyzer `analysis.zip` / `trajectories.json` from the analysis response `trajectoriesFileinfo` URL (controller uploads this during clustering). |
| `collision.json` | Export from Payload: for each trial in batch, read `testObjectives.criticalityMetrics` where KPI `name == "collision"` → `{ "<trial_id>": true/false }`. (Senior’s `collision.json` follows this shape.) |
| Heatmaps | Optional PNGs from Dashboard heatmap export / `fullHeatmaps` documents. |

**Clustering settings to match paper bundle (starting point):**

```json
{
  "method": "hdbscan+mfpca",
  "nClusters": 0,
  "minClusterSize": 20,
  "minSamples": 3,
  "clusterSelectionEpsilon": 1.5,
  "clusterSelectionMethod": "eom"
}
```

Tune in **Clustering Selection** until silhouette / cluster count aligns with paper figures.

**Optional CLI** (same backend as Dashboard):

```bash
# Analyzer must be running on :9010
curl -X POST http://localhost:9010/trajectory_analysis \
  -H "Content-Type: application/json" \
  -d '{"batchIds":["<batch_id>"],"framePeriod":0.1,"tasks":[{"method":"hdbscan+mfpca","minClusterSize":20,"minSamples":3,"clusterSelectionEpsilon":1.5,"clusterSelectionMethod":"eom"}]}'
```

## 12. Quick troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Dashboard **Analysis** click, then nothing | Analyzer down, Payload URL mismatch, or long silent run | Confirm `curl -s http://localhost:9010/schema`; align `app/analyzer/.env` with dashboard Payload URL; watch Network + `analyzer.log` (see **§2 Q2b**) |
| **Analysis** spinner ~30+ min | Default **488** HDBSCAN tasks in `Saves/index.tsx` | Wait, or POST one task via curl (§10 Phase D) for a smoke test |
| **save** does nothing useful | Analysis never completed | Run **Analysis** first; open **Clustering Selection** to confirm results loaded |
| `No module named 'data'` in `generate_map_tracks.py` | Stale import after flat `src/` layout | Fixed: `from dataset_config import …` |
| `No medoids computed` for dataset3 | Zero overlap between clustering trials and local `esmini_3_*.csv` | Sync batch-3 CSVs or `--trials '3:0,3:1,...'` |
| BEV step “hangs” on dataset2 | Huge CSV (~38k rows) + old O(n²) code | Fixed in `tier2_renderer.py` (June 2026) |
| `exact medoid CSV missing, using nearest` | Normal for sparse cache | Sync more CSVs or accept approximate medoid |
